# Security review — September 2026

Story: MSHWAR-114 · Scope: API, database migrations 001–026, web app, CI and container images · Method: the [threat model](threat-model.md), a code walk-through of each surface, automated checks, and the new test suites

## How to read this

- **Severity**: High, Medium, Low (likelihood × impact for this product today).
- **Status**:
  - _Resolved_: fixed and covered by a test.
  - _Accepted_: a conscious decision, with a reason and a follow-up.
  - _Open_: needs someone outside the code.

## Findings

| ID    | Severity | Finding                                                                                                                                                                 | Status                     | Resolution                                                                                                                                                                        |
| ----- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SR-01 | High     | Access checks were spread across handlers. Any signed-in user could create catalogue collections, and any business member could record revenue events for any business. | Resolved                   | One declared policy per route, checked at start-up; admin-only collections; `capture_org_event` checks membership. Tests: `test_access_policies.py`, `test_idor.py`.              |
| SR-02 | High     | The API could run as a superuser, which silently skips row-level security. Some code read tables directly, and some job functions ran with the caller's rights.         | Resolved                   | `mshwar_api` login role with a start-up check; direct reads moved into functions; job functions made `SECURITY DEFINER`; CI runs every test as the restricted role.               |
| SR-03 | Medium   | Cookie-authenticated writes relied only on `SameSite=Lax` against cross-site requests.                                                                                  | Resolved                   | Cross-site request guard (`app/core/csrf.py`); `PUBLIC_WEB_ORIGIN` must be https when deployed. Test: `test_csrf.py`.                                                             |
| SR-04 | Medium   | Revoking another business's invitation or blackout returned `200 {"ok": false}`, revealing that the record exists.                                                      | Resolved                   | Returns 404. Test: `test_idor.py`.                                                                                                                                                |
| SR-05 | Medium   | Unsubscribe tokens were stored in plain text and returned by the preferences endpoint.                                                                                  | Resolved                   | Tokens are stored hashed in `unsubscribe_tokens`; no longer returned. Test: `test_notifications.py`.                                                                              |
| SR-06 | Medium   | `notification_templates` had no row-level security.                                                                                                                     | Resolved                   | RLS with a read policy (migration 024). Test: `test_db_contracts.py`.                                                                                                             |
| SR-07 | Medium   | Rate limits were per process, and planner calls had no spending limit.                                                                                                  | Resolved                   | Redis-backed limits (required when deployed); per-person and platform AI ceilings; metrics and alerts. Test: `test_abuse_controls.py`.                                            |
| SR-08 | Medium   | Uploads were checked by declared type and first bytes only; no structure checks, quotas or upload rate; documents could be served inline.                               | Resolved                   | Structure inspection, quotas, hourly limit, sandboxed download headers, ImageKit for listing photos. Test: `test_abuse_controls.py`, `test_portal.py`.                            |
| SR-09 | Medium   | Logs and error reports could include secrets or personal data; there was no way to connect a user's error to the logs.                                                  | Resolved                   | Central scrubber on logs and Sentry; request IDs end to end. Test: `test_scrubber.py`, `scrub.test.ts`.                                                                           |
| SR-10 | Medium   | The audit log could be changed by the backend role, and many consequential tables weren't audited.                                                                      | Resolved                   | Append-only triggers; no table rights for the API role; generic audit trigger; admin search. Test: `test_audit_coverage.py`, PGlite suite.                                        |
| SR-11 | Low      | Validation errors echoed the submitted values, including passwords.                                                                                                     | Resolved                   | 422 bodies list fields and messages only. Test: `test_access_policies.py`.                                                                                                        |
| SR-12 | Low      | Sign-up says when an email is already registered, so accounts can be enumerated.                                                                                        | Accepted                   | Needed for a clear sign-up experience. Limited by the `auth-register` rate limit (30 per hour per IP); sign-in and reset don't reveal it. Revisit if abuse is seen.               |
| SR-13 | Low      | The Content Security Policy allows `'unsafe-inline'` scripts and styles, because Next.js inlines its start-up scripts.                                                  | Accepted                   | Other directives are strict (`object-src 'none'`, `frame-ancestors 'none'`, fixed frame and connect sources). Follow-up: nonce-based CSP through `proxy.ts`.                      |
| SR-14 | Medium   | Admin accounts have no second factor.                                                                                                                                   | Accepted (decision needed) | Elevated tier for the most sensitive actions, full audit trail, sign-in rate limits. **Recommended follow-up story: MFA for admin accounts before launch.**                       |
| SR-15 | Low      | Seven advisories in the test toolchain (vitest 2.1 → vite, esbuild). Fixes need a major upgrade (vitest 4).                                                             | Accepted                   | Not in production images; the Vitest UI server isn't used; CI blocks advisories in production dependencies. Follow-up: plan the vitest upgrade.                                   |
| SR-16 | Low      | Python dependencies use minimum versions without a lock file, so builds can change over time.                                                                           | Accepted                   | pip-audit and Dependabot in CI; the container scan checks the built image. Follow-up: add a lock file.                                                                            |
| SR-17 | Medium   | Business cancellations were refunded under the customer's cancellation terms, which could mean a partial refund.                                                        | Resolved                   | Business cancellations always refund in full (migration 026). Test: `test_consent.py`.                                                                                            |
| SR-18 | Low      | Browser error reporting and Google Maps could load before the visitor agreed.                                                                                           | Resolved                   | Cookie choices default to essential only; both wait for consent. Tests: `cookie-consent.test.ts`, `experiences-map.consent.test.tsx`.                                             |
| SR-19 | Medium   | Terms, privacy policy and cancellation policy are drafts that haven't had legal review.                                                                                 | Resolved                   | Reviewed by a Lebanese lawyer on 18 September 2026, versions `2026-09-16` of terms, privacy, cancellation and community; no changes requested. `NEXT_PUBLIC_LEGAL_REVIEWED=true`. |
| SR-20 | Medium   | No independent penetration test yet.                                                                                                                                    | Open                       | Book one before launch, using the threat model as its scope.                                                                                                                      |
| SR-21 | Low      | `img-src` in the CSP allows any https host.                                                                                                                             | Accepted                   | Images carry no script. Follow-up: narrow to the ImageKit endpoint once the catalogue uses it everywhere.                                                                         |
